## 1. Mediation Principle: Clients Never Talk to Supabase Directly

ADR-0002 states this as a condition of the polyglot-persistence decision, not an optional convention: *"The Node.js/TypeScript backend (per ADR-0001) is the only layer permitted to talk to both stores. No client (mobile app, admin dashboard, security-company dashboard) talks to Supabase or MongoDB directly — all access is mediated through the backend API."*

This backend approach confirms and details that principle for Feature 001 specifically:

- **No client SDK for Supabase Auth ships to the mobile app, admin dashboard, or security-company dashboard.** Supabase provides official client SDKs (`@supabase/supabase-js`, mobile equivalents) that would let a client call Supabase Auth directly — signup, login, token refresh, MFA challenge — bypassing the backend entirely. This is explicitly rejected. The only Supabase client present anywhere in the system is a **server-side Supabase client (service-role / admin API key) inside the Node.js/TypeScript backend**.
- **Why this matters beyond ADR-0002's stated rationale:** if clients called Supabase Auth directly, every backend-enforced business rule in Section 3 below (BR-2, BR-3, BR-4, BR-6, BR-7) would have to be re-implemented as a Postgres Row-Level-Security policy or Supabase Auth hook/trigger, and every client (mobile, two dashboards) would need to independently and correctly apply it — multiplying both the attack surface and the number of places a rule can drift out of sync. Routing everything through the backend means these rules exist in exactly one place, and none of them depend on trusting the client to apply a check.
- **What this looks like concretely:** the mobile app / admin dashboard / security-company dashboard call the platform's own `/v1/auth/*` and `/v1/session/*` endpoints (Section 2) with normal HTTPS JSON requests, exactly like any other domain endpoint. The backend, on receipt, calls Supabase Auth's server-side Admin/GoTrue API on the client's behalf, applies the platform's business rules before or after that call as appropriate, and returns the platform's own response shape — never Supabase's raw response — to the client. Session tokens issued to clients are the tokens the backend hands back after this mediation, not a token a client obtained by talking to Supabase itself.
- **Consequence for token validation on subsequent requests:** every authenticated request to any other backend service (asset registry, policy/subscription, claims, notification-dispatch — none built yet, but this sets the pattern) validates the bearer token via the backend's own auth-verification middleware, which in turn validates the Supabase-issued JWT (using Supabase's public JWKS, not a Supabase round-trip on every request) plus applies platform-specific claims (role, `mfa_required`, partner-org scope — see Section 3). This keeps token verification fast (local JWT verification, no network call per request) while keeping issuance and mutation entirely backend-mediated.

**This is a hard architectural constraint for Stage 6/7, not a preference:** any future engineer proposing a client-side Supabase SDK integration for auth is proposing a deviation from ADR-0002 and this approach, and must route that through a new ADR, not a PR.

## 2. Service Decomposition and Endpoint Groupings

### 2.1 Where this sits in the broader service map

Per ADR-0001's Node.js/TypeScript baseline, the backend decomposes into services grouped by domain ownership, not by client surface (mobile vs. web dashboards share services; they do not get separate backends). Feature 001 stands up the first of these:

- **Identity Service (this feature's home)** — owns everything in Section 2.2 below. System of record: Supabase (Postgres + Supabase Auth), per ADR-0002. This is the only service in the platform permitted to hold a Supabase service-role credential.
- *(Not built in this feature, named only to show where Identity Service's boundary sits):* Asset-Registry Service, Policy/Subscription Service, Claims Service, Notification-Dispatch Service, GPS-Ingestion Service — all MongoDB-backed per ADR-0001/ADR-0002, all depending on Identity Service for `account_id` resolution and role/session validation, none depending on each other for auth.

Identity Service is deliberately the **narrowest, most isolated** service in the platform: it has no business logic dependency on any other service (nothing else needs to exist for signup/login/MFA to work), while everything else depends on it. This is intentional — it is both the first thing built (per the product-plan.md sequencing rationale: "provisioning/identity primitives before login... before session mechanics") and the hardest single point of failure to tolerate being down, so it is kept small and isolated rather than accreting unrelated responsibilities.

### 2.2 Endpoint groupings (named and grouped — full request/response schemas are Stage 7)

All endpoints versioned from day one under `/v1/...` per the API design standard. Grouped by the 17-story backlog in `product-plan.md` §4:

| Group | Endpoints (illustrative, not final naming) | Backlog stories covered | Surface(s) |
|---|---|---|---|
| **Signup & verification** | `POST /v1/auth/signup`, `POST /v1/auth/verify-email`, `POST /v1/auth/resend-verification` | #2, #3 | Mobile (customer only — no admin/security-company/support equivalent exists here, by design, per BR-3) |
| **Invitation & privileged provisioning** | `POST /v1/invitations` (admin-issued, creates invite), `GET /v1/invitations/:token` (invitee views invite details — email, org name for security-company operators), `POST /v1/invitations/:token/accept` (sets password, transitions invite → account) | #4, #5 | Admin Dashboard (issuing), Web (Admin/Security-Company Dashboard invite-acceptance screen) |
| **MFA enrollment** | `POST /v1/mfa/enroll` (returns QR/manual-key payload), `POST /v1/mfa/enroll/verify` (confirms TOTP code, completes enrollment) | #6, #10 (customer opt-in reuses the same endpoints) | Web (mandatory, privileged), Mobile (optional, customer) |
| **Login & session issuance** | `POST /v1/auth/login` (password step; returns either a session or an `mfa_required` challenge token), `POST /v1/auth/mfa/challenge` (submits TOTP code, completes login and issues session) | #7, #8, #9 | All three client surfaces |
| **Logout & session management** | `POST /v1/session/logout` (current session), `POST /v1/session/logout-all` (used internally by password-reset finalization, FR-17; also exposed as an explicit user-facing "log out everywhere" action if product wants it later), `POST /v1/session/refresh` | #11, #12, #13, #16 | All three client surfaces |
| **Password reset** | `POST /v1/auth/reset-password/request`, `POST /v1/auth/reset-password/confirm` (privileged-role variant requires an additional `POST /v1/auth/reset-password/mfa-verify` step before finalization, per FR-18/AC-10) | #14, #15 | All three client surfaces |
| **Account-state / compliance support** | `GET /v1/account/me` (current account state, role, MFA status — drives client-side gating UI, e.g. §1.8's BR-2 gate screen), internal-only account-state transition hooks (not client-facing) | Implicit across #1, #3 | All three, read-only for the client |
| **Audit log (internal/admin surface only)** | `GET /v1/admin/audit-log` (admin/compliance query surface — not customer-facing, RBAC-gated to admin/support/compliance-tooling roles only) | #17 | Admin Dashboard only |

**Grouping rationale:** invitation/provisioning is deliberately its own group, separate from signup — this mirrors BR-3's hard separation (no shared code path between "anyone can hit this" and "only an existing admin can trigger this"), and makes it structurally obvious at the routing layer, not just the business-logic layer, that there is no self-service path to a privileged role. MFA enrollment is its own group because it is shared infrastructure between mandatory (privileged) and optional (customer) flows — one implementation, two policy callers, per the "no admin bypass without a `cto`-signed risk acceptance" requirement in BR-4, which is easier to defend when there is exactly one enrollment code path to audit rather than two.

### 2.3 API design standards applying to this endpoint set

- **Versioning:** `/v1/` from day one, per `backend-architect`'s standing practice; no endpoint above ships unversioned.
- **Error envelope:** consistent `{ error: { code, message } }` shape across all groups, with anti-enumeration endpoints (`signup`, `reset-password/request`) returning the **same envelope shape and same HTTP status** regardless of whether the underlying identifier exists — this must be true at the wire level, not just in the message text, or a client (or an attacker inspecting timing/status codes) can still enumerate. **Flag for Stage 7:** confirm Supabase Auth's own default responses for duplicate-signup and password-reset-for-unknown-email don't leak a distinguishable status code before the backend's normalization layer is designed around them.
- **Idempotency:** invitation issuance (`POST /v1/invitations`) and privileged-role state-mutating admin actions get mandatory idempotency-key support, per this role's Best Practice ("idempotency keys mandatory on all mutating endpoints tied to money or device state") extended here to privileged-account provisioning, since a duplicate invitation send/accept race is a security-relevant mutation (could create ambiguity about which invitation token is authoritative), not merely a UX annoyance. Signup and login are naturally idempotent-safe by their own semantics (duplicate signup is rejected by BR-6; duplicate login just re-authenticates) and do not need a separate idempotency-key mechanism.
- **Pagination:** applies to `GET /v1/admin/audit-log` only, in this feature's scope — the one list-shaped endpoint. Standard cursor-based pagination, consistent with whatever platform-wide convention Stage 7 ratifies for every other future list endpoint (asset lists, policy lists) — not invented uniquely for audit logs.
- **Rate limiting:** see Section 5.

## 3. Business Rules Layered on Top of Supabase Auth

ADR-0002 already performed an FR-by-FR coverage analysis (its "What Supabase Auth buys" section). This section restates that analysis at the enforcement-point level — **who enforces what, and where** — which is the backend-architecture-specific question ADR-0002 deferred to this stage.

| Business rule | What Supabase Auth gives natively | What the backend must add, and where |
|---|---|---|
| **BR-2 — verification gates commerce** | Email-confirmation flow, `email_confirmed_at` field | Supabase has no concept of "commerce-gated action." The backend's account-state derivation (`pending_verification` → `active`, per BR-5) is computed from Supabase's `email_confirmed_at` at the Identity Service boundary and exposed via `GET /v1/account/me` and an internal claim on the issued session token. **Enforcement point:** every *other* service that owns a commerce-gated action (future Policy/Subscription Service, future Asset-Registry Service) must check this claim/state before allowing the action — this is a contract Identity Service publishes (an `account_state` field on the token or a lightweight internal lookup), not something Supabase or Identity Service can enforce on another service's behalf. Flagged forward to whichever service builds policy purchase / asset registration: **the gate check is the consuming service's responsibility, not Identity Service reaching into it.** |
| **BR-3 — invitation-only privileged provisioning** | Supabase Auth's admin-invite primitive (sends an invite email, mechanism-level) | The *business workflow* — who may call the invite-issuance endpoint (admin-role check), org-scoping for security-company operators (BR-7), forced first-login password+MFA flow, and the structural absence of any public signup route for these three roles — is entirely backend logic, enforced at the API-routing layer (separate endpoint group, Section 2.2) and at the authorization-middleware layer (only an authenticated admin session can call `POST /v1/invitations`). Supabase's invite mechanism is used only as the underlying "create a Supabase Auth user in an unconfirmed/invited state and send the email" primitive; the backend owns the invitation record's lifecycle (issued → accepted → expired), not Supabase. |
| **BR-4 — mandatory MFA for admin/security-company-operator/support-agent** | A TOTP enrollment/challenge primitive exists in Supabase Auth (mechanism) | Supabase has no concept of "this role must have MFA, cannot disable it, cannot skip it." This is a platform-specific authorization policy enforced in the backend's login-flow logic: on successful password verification, the backend checks the account's role; if role ∈ {admin, security-company-operator, support-agent}, the backend refuses to issue a session until an MFA challenge succeeds, and — separately — refuses to mark the account as fully provisioned (first-login gate) until MFA enrollment is complete. **This must be enforced server-side in Identity Service, never inferred from client-side routing** (a client simply not showing the MFA screen is not enforcement — AC-6/AC-7 language ("not just at the client") is a direct instruction to build this check in the backend, matching `06-security-standards.md`'s "server-side, not just at the client" line). No admin bypass path exists in the API surface at all — the documented `cto`-signed risk-acceptance override, if ever exercised, is an out-of-band operational action (e.g., a manual database intervention with its own audit trail), not a code path the API exposes. |
| **BR-6 — one email, one account** | Supabase Auth enforces a unique-email constraint on its own `auth.users` table natively | This one is largely native — Postgres uniqueness on email is exactly what Supabase Auth already does. The backend's job here is narrower than for the other rules: (1) normalize the anti-enumeration response (FR-5, AC-2) so a duplicate-signup rejection doesn't leak existence via a different status/error shape than a generic failure, and (2) ensure this uniqueness constraint is the *only* identity key the rest of the platform trusts — no service should independently key on phone number or any other field as an alternate uniqueness check, consistent with BR-1's "email is the sole mandatory primary identifier" ratification. |
| **BR-7 — partner-org scoping at creation** | Nothing — Supabase Auth has no concept of a partner organization | Fully backend-owned. The invitation-issuance endpoint (`POST /v1/invitations`) requires and validates a `partner_org_id` for security-company-operator invitations specifically (not for admin/support invitations), and this association is persisted as platform data alongside the Supabase account reference — **flagged to `database-architect` at Stage 6:** this is exactly the kind of relationally-shaped, identity-adjacent data (an account's org membership) that could live either as a Postgres table alongside Supabase Auth's own tables (same database, same consistency domain) or as backend-owned metadata — Stage 6 should resolve which, but either way it is **not** a Supabase Auth native concept and the backend must own writing and validating it at invitation time, not assume Supabase captures it. |

**Net pattern across all five rules:** Supabase Auth is trusted for *mechanism* (hashing, token issuance, TOTP cryptography, unique-constraint enforcement) and never trusted for *platform-specific policy* (who gets MFA, who can invite whom, what "verified" unlocks). This mirrors ADR-0002's own framing exactly, restated here as an enforcement-point map rather than a coverage checklist.

## 4. Cross-Database Reference Pattern: MongoDB → Supabase `account_id`

ADR-0002 already names this pattern and its central risk ("no cross-database referential integrity... this burden falls on `backend-architect`/`backend-engineer`"). Confirming it is workable, and specifying what the backend must own to keep it consistent:

**Is it workable?** Yes, with conditions — this is a standard pattern for polyglot-persistence architectures (a stable, immutable, opaque reference ID crossing a system boundary), and it is *especially* workable here because the reference is one-directional and low-cardinality-per-write: a MongoDB `policy`/`asset`/`claim` document references exactly one `account_id` at creation and that reference essentially never needs to change (an asset doesn't get reassigned to a different Supabase account in this feature's scope — BR-6/multi-user accounts are explicitly out of scope). This is a much easier consistency problem than, say, a bidirectional or frequently-mutated cross-database reference would be.

**What the backend must own to keep it consistent, concretely:**

1. **Write-time validation (existence check).** Before any MongoDB write that sets an `account_id` reference (asset registration, policy creation — not built in this feature, but this is the contract they must follow), the owning service must call Identity Service (or validate a trusted, recently-issued token's claims) to confirm the referenced account exists and is in an appropriate state (e.g., `active`, per BR-2's gate). This replaces the foreign-key check Postgres would normally give for free. **This is the single most important thing to get right, and it is cheap** — in practice this check is usually already happening anyway, because the same request is authenticated and the `account_id` typically comes from the caller's own validated session token, not from unvalidated client input. The higher-risk case is a *background/async* process (e.g., a scheduled job, a webhook-triggered write) creating a MongoDB document against an `account_id` that isn't the live request's own session — those paths need an explicit existence check, not an assumption.
2. **Deletion/deactivation propagation — the harder, standing obligation.** ADR-0002 correctly flags this as the real risk: *"if a Supabase account is hard-deleted... MongoDB will silently retain orphaned policy/asset/claim documents."* The backend must own an explicit mechanism here, not a "we'll notice eventually" assumption. This feature (Feature 001) does not itself delete accounts (BR-5's states stop at `deactivated`, and Stage 1's compliance review — business-requirements.md §9.2(b) — already flags that `deactivated` needs an eventual real-deletion path as a **future** POPIA-driven feature, not this one). But the architecture must anticipate it now so it isn't a redesign later:
   - **Recommendation for Stage 6/7:** Identity Service should treat account deletion/anonymization as an event it publishes (not a silent database operation), even before an event bus exists elsewhere in the platform — at minimum, a backend-owned outbox-style record ("account X was hard-deleted/anonymized at time T") that other services can poll or that a future event-bus integration can pick up, rather than a bare `DELETE` against Supabase with no trace. This directly addresses ADR-0002's Revisit Trigger risk ("cross-database referential-integrity failures... surface in practice at a rate the backend-level enforcement isn't catching") by making deletion an observable, not-silent event from day one, even while the actual downstream MongoDB cleanup logic belongs to a later feature.
   - **What Feature 001 must ship now, not defer:** the `deactivated` state transition itself (already in scope, BR-5) and its audit trail. What Feature 001 should **not** attempt: automatic MongoDB cleanup logic, since no MongoDB collections referencing `account_id` exist yet (asset/policy features aren't built). This is explicitly a forward-compatibility design note, not new scope for this feature.
3. **No cross-database transactions — compensating-action awareness.** Any future operation that needs to create a Supabase account *and* a MongoDB document in the same logical action (not present in this feature's own scope, since Feature 001 only creates Supabase-side records) must be designed as a saga (create Supabase record first, since it's the identity anchor; MongoDB write second; explicit compensating action — mark the Supabase account for cleanup — if the MongoDB write fails) rather than assumed atomic. Feature 001 itself has no such dual-write today, so this is a note for the next feature that does, not a gap in this one.

**Verdict: workable, with the deletion-propagation mechanism as the one item that must be designed (as an event/outbox pattern) even though it isn't implemented until a later feature owns actual account deletion.** This should be explicitly logged as a forward dependency for whichever future feature implements POPIA-driven account deletion (flagged in business-requirements.md §9.2(b) already), so Identity Service's event-publishing hook is built once, correctly, rather than retrofitted.

## 5. Rate-Limiting/Lockout Enforcement Point, and Where Audit Events Are Written

### 5.1 Rate-limiting / lockout (FR-11)

**Enforcement point: custom backend layer, not assumed-sufficient from Supabase's baseline throttling.**

- Supabase Auth applies some baseline rate limiting at the platform level (e.g., generic abuse protection on its hosted endpoints), but ADR-0002 is explicit that "FR-11: rate-limiting/lockout thresholds and BR-4's exact re-prompt cadence are policy decisions still owned by `authentication-engineer`/`security-engineer`, layered on top of whatever baseline throttling Supabase provides." This backend approach confirms that framing: **the backend, not Supabase, is the system of record for "has this account/IP exceeded the failed-attempt threshold,"** because only the backend can apply the platform-specific policy this requires — a distinct counter for password attempts vs. MFA attempts (per ux-research.md §1.2's explicit instruction not to conflate them), the pre-lockout warning UX (§1.2 step 6, which requires the backend to expose "attempts remaining" as data, not just a pass/fail), and the escalation copy differences between customer and privileged-role lockouts.
- **Where this lives architecturally:** a lightweight, fast-read counter store fronting the login/MFA-challenge endpoints — most naturally implemented as a Redis-backed (or equivalent in-memory/fast-KV) rate-limit layer sitting in front of Identity Service's login/MFA endpoints, keyed on account identifier and/or source IP, **not** inside Supabase Postgres (a relational write-per-attempt for something this high-frequency and short-lived is the wrong tool, and would also blur the line between "authentication data" that belongs in Supabase per ADR-0002 and "ephemeral abuse-mitigation counters" that don't need the same durability guarantees). This is a Stage 6/8 sizing detail (`security-engineer`/`site-reliability-engineer` own the concrete technology choice), but the architectural placement — in front of, not inside, Supabase — is a Stage 5 decision this document is making now.
- **Confirmed to `cybersecurity-architect`/`security-engineer` for Stage 8:** exact thresholds, backoff curve, and IP-vs-account-vs-both keying strategy remain explicitly deferred per FR-11's own text ("exact thresholds deferred to `authentication-engineer`/`security-engineer`") — this document only fixes *where* the enforcement lives, not the numbers.

### 5.2 Audit-log write point (FR-12, FR-17, compliance §9.3's 12-month retention ruling)

**Enforcement point: backend-owned audit table, not Supabase Auth's own internal logs.**

- Supabase Auth does not provide a compliant, purgeable audit log as shipped (ADR-0002: "this needs its own table/mechanism, designed jointly by `database-architect` and `security-engineer`"). Architecturally, the audit log is a **backend-written record**, produced synchronously at the point Identity Service completes each auth-relevant action — login attempt (success/failure), logout, password-reset request/completion, MFA enrollment/verification, account-state transition — not derived after the fact from Supabase's own logs, and not dependent on Supabase retaining anything for the 12-month window (POPIA retention obligations, business-requirements.md §9.3, attach to *our* store, which we control the deletion mechanics of — Supabase's own internal logging retention is a separate, unrelated concern we do not rely on to satisfy this compliance requirement).
- **Where it's written, storage-wise — this is a genuine Stage 6 open question this document flags rather than resolves:** two credible options, both consistent with ADR-0002's domain boundary:
  1. **A Postgres table in the same Supabase project**, alongside the identity data it describes — argues for itself on consistency (audit events about an account live next to the account, same transactional boundary at write time, easy to query "everything about account X" in one place) and is the more natural reading of ADR-0002's own scope ("accounts, account states... and authentication audit events" are explicitly named together as Supabase's domain in the ADR's Decision section).
  2. **A MongoDB collection**, on the reasoning that audit events are naturally append-only, time-series-shaped, high-volume-over-time records — a pattern ADR-0002 itself already earmarks MongoDB as well-suited for (its Alternative-2 rejection explicitly calls out MongoDB's "native time-series collection support" as a reason not to move everything to Postgres).
  - **This document's recommendation, not a final decision:** option (a), Postgres/Supabase, because ADR-0002's Decision section already explicitly named "authentication audit events" as part of Supabase's domain — treating them as MongoDB's instead would quietly contradict the ADR's own stated scope without a documented reason to reopen it. `database-architect` should ratify or override this at Stage 6 with the indexing/retention-purge-job design in mind (the automated 12-month purge job compliance-specialist specified in business-requirements.md §9.3 needs to be built against whichever store is chosen — that job design is Stage 6/9 work, not this document's).
- **Retention/purge mechanics** (12-month automated purge, legal-hold carve-out, meta-audit of the purge job itself) are exactly as specified in business-requirements.md §9.3 — this document does not restate that design, only confirms the write-point decision it depends on (audit events land in a backend-owned, purgeable store from the moment they're written, never assumed to inherit Supabase's own undefined internal retention).
- **The `GET /v1/admin/audit-log` endpoint (Section 2.2)** reads from this same store and is itself RBAC-gated (admin/compliance-tooling roles only) and rate-limited/paginated like any other list endpoint — it is not a raw database export.

### Blocking concern flagged for Stage 5 exit

**Supabase outage/degradation fallback is not designed anywhere yet, including in ADR-0002.** ADR-0002's "Real costs of the split" section names *operational* cost (two systems to run) and *compliance* risk (data residency) as open follow-ups, but does not address **what happens to login/signup/session-refresh when Supabase Auth itself is unreachable or degraded** — this is a genuine gap, not a nitpick, because Identity Service is the single most depended-upon service in the platform (Section 2.1) and its upstream dependency (Supabase) is entirely third-party-hosted with no fallback path specified. Per this role's own Best Practice — *"Design for GPS/security-company vendor outages: queue and retry, never block core... flows on a third-party call"* — the equivalent principle applies here even more acutely, since Supabase isn't a peripheral integration, it *is* the identity system.

This does not block Stage 5 exit on its own (no code is being written yet, and the fallback strategy is properly a Stage 6/8 design detail, informed by `site-reliability-engineer`/`cybersecurity-architect`), but it is logged here as a **named, tracked item that must be resolved before Stage 8 (Security Review) sign-off**, not discovered at incident time: at minimum, Stage 6/8 must define (a) what a client sees if login is attempted during a Supabase outage (a clear degraded-state error, not a hung request or an ambiguous failure), (b) whether already-issued sessions remain valid and usable for read-only/non-auth-mutating actions during an outage (since JWT verification via cached JWKS does not require a live Supabase call, this is likely "yes" for session validation but "no" for login/signup/MFA/password-reset — worth confirming explicitly, not assumed), and (c) an incident/monitoring hook so `site-reliability-engineer` knows the moment Supabase degrades, given every other service's auth checks are downstream of it.

### Overall sign-off status

**Approved to proceed to Stage 6 (Database Design) and Stage 7 (API Design), with one tracked blocking item for Stage 8 exit (Supabase outage/degradation fallback design, above) and two items explicitly deferred with clear owners (audit-log storage location — Postgres vs. MongoDB, recommendation given but not finalized, owner `database-architect` at Stage 6; deletion-propagation event/outbox mechanism — designed in principle here, implementation owned by the future account-deletion feature).**

This approach is sound as a decision-level design: it confirms ADR-0002's mediation principle with no exceptions, gives Stage 6/7 a concrete, named endpoint surface to build schema and OpenAPI contracts against, maps every backend-enforced business rule to a specific enforcement point rather than leaving any of BR-2/BR-3/BR-4/BR-6/BR-7 ambiguously "somewhere in the backend," confirms the cross-database reference pattern is workable with one clearly-scoped standing obligation (deletion propagation) rather than an open-ended risk, and places rate-limiting and audit-logging in specific, justified architectural locations rather than assuming Supabase provides either. The one blocking concern (Supabase outage fallback) is flagged with a concrete resolution path and owner, consistent with this role's practice of naming risks explicitly rather than absorbing them silently.
