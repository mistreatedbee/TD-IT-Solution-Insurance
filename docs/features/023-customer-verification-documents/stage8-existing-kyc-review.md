# Customer identity verification (KYC) — Stage 8 security review (security-engineer)

- **Date:** 2026-11-20. **Source:** `origin/main` (read with `git show`; nothing was run).
- **Scope:** `backend/src/routes/customer-profile.ts`, `backend/src/routes/admin-verification.ts`, `backend/src/lib/customer-profile-serializer.ts`, `backend/src/lib/customer-profile-validation.ts`, `backend/src/repositories/customer-profiles.ts` (submit and review), `src/admin/pages/AdminVerificationPages.tsx` (Queue and Review pages, routed at `src/admin/AdminRoutes.tsx:102-103`), and the mobile gates on `mobile/app/(app)/(tabs)/account/{profile,verification}.tsx`.
- **Verdict, owner-test build (no real users or data): CONCUR.** None of the findings is exploitable by an outside party.
- **Verdict, real users: BLOCK until KYC-1 and KYC-2 are fixed and KYC-3 has a ruling from `cybersecurity-architect` and `compliance-specialist`.** A security-engineer review alone does not complete Stage 8. Cybersecurity-architect and compliance concurrence are still needed.

## What is sound
- **Object-level authZ (IDOR):** clean. Every customer route uses only `req.auth.accountId` (`customer-profile.ts:61,90,183,224,280,306`), so no client-supplied id reaches a query. Admin routes use `requireUserType('admin')` and validate `:id` as a UUID (`admin-verification.ts:17,35,94,128,192`). The decision PATCH also requires the subject to be `userType === 'customer'` (`:227`).
- **Step-up:** the decision PATCH runs `requireStepUp` before any read or write (`admin-verification.ts:201`), and the admin UI handles the retry (`AdminVerificationPages.tsx:93,277`).
- **Race:** `expectedRevision` is checked atomically inside the `findOneAndUpdate` filter (`customer-profiles.ts:460`).
- **Rate limits:** every route has one. Submit is limited to 5 per hour (`customer-profile.ts:178`), the decision to 30 per 15 minutes (`admin-verification.ts:195`), and the list and count to the audit-read limit.
- **ID number:** only the last 4 digits ever reach the API. The Zod check is `^[0-9]{4}$` (`customer-profile-validation.ts:21-25`, CT-11). Responses mask it (`serializer:60`, `admin-verification.ts:60`).
- **Input validation:** `.strict()` Zod schema with length limits (`customer-profile-validation.ts:10-44`). The decision is an enum and the reason is limited to 500 characters (`admin-verification.ts:19-26`). No user input reaches a query operator, so there is no NoSQL-injection path.
- **Identity reads are audited:** the list writes `recordBulkDisclosure` before responding (`:68`), and the detail view writes `privileged_data_access` before serialising (`:154`).
- **Logs:** there are no `console` or `logger` calls in these files.

## Findings

| ID | Sev | Location | Finding | Remediation |
|---|---|---|---|---|
| KYC-1 | **Medium** | `admin-verification.ts:233-262` | The decision is written (`reviewVerification`) **before** both audit rows. If the audit write fails, the verification status has changed with no audit record, and the admin only sees a 500. This is not fail-closed (AUD-10). | Write the audit rows first and fail the request if that write fails. Alternatively, use a transaction or outbox so the state change and its audit record commit together. Add a test with a failing audit write. |
| KYC-2 | **Medium** | `customer-profile.ts:51,79,173`; `customer-profiles.ts:389` | The customer profile routes have no `requireUserType('customer')`. Admin and security-company staff accounts can create a profile (`getOrCreateForAccount`) and submit it, so a staff identity appears in the admin queue. The PATCH later returns 404 for it (`:227`), so the queue entry cannot be resolved. The routes also have **no backend `FEATURE_KYC_ENABLED` gate**: the flag exists only in mobile (`mobile/src/config/features.ts:46`), so these endpoints are live in production whatever the flag says. | Add `requireUserType('customer')` to every `/account/profile*` route. Add a server-side KYC flag that returns 404 when off, matching how other flags gate features. |
| KYC-3 | **Medium (design; escalate to cybersecurity-architect and compliance)** | `admin-verification.ts:189-304`; `AdminVerificationPages.tsx:191-223` | The admin "verifies" identity using only self-asserted name, DOB, address and the last 4 ID digits. There is no document, no checksum against the full number, and no third-party check. A comment calls `verified` "a trust primitive other controls key off" (`:198`), but nothing backs it. The status can be faked by anyone who enters plausible data. | Before real users, either rename and limit the status ("details reviewed") so no control treats it as proof of identity, or block real-user use until Feature 023 (documents) lands. List every control that depends on `verificationStatus`. |
| KYC-4 | Low | `admin-verification.ts:170-181`; `AdminVerificationPages.tsx:205-223` | The detail view returns and shows full DOB, full residential address, and the emergency contact's name and full phone number. The emergency contact is a third party, and their data is not needed for an identity decision (POPIA minimality). The read is audited. | Mask the emergency-contact phone, or leave it out of the admin verification payload. Ask compliance whether the full address is needed. |
| KYC-5 | Low | `admin-verification.ts:125-187` | The detail GET looks up the account with `findByIdForAdminDetail` and has no `userType === 'customer'` check, unlike the PATCH. Any account that has a profile can be read (see KYC-2). | Add the same customer check to the GET. |
| KYC-6 | Low | `sync-account-alerts.ts:80` | The admin-written `rejectionReasonCustomerSafe` text is shown word for word in a customer alert. It is already a noted residual in `stage8-manifest.json:163`. React escapes it, so there is no XSS risk, but an admin could put misleading or phishing text in front of a customer. | Offer reviewers a set list of reasons plus a short optional note, and refuse URLs in the note. |
| KYC-7 | Low | `customer-profile-validation.ts:15` | `dateOfBirth` accepts any calendar date, including future dates and dates 200 years ago. | Limit it to a plausible adult range, for example ages 18 to 120. |
| KYC-8 | Info | `customer-profiles.ts:389-423` | Submit has no state guard, so a `verified` customer can resubmit and return to `pending_review`. This only lowers trust and is limited to 5 per hour, but it does make queue noise possible. | Optional: allow submit only from `not_started`, `rejected` or `action_required`. |
